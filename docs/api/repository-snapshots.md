# Repository baselines, sealed results and caches

`POST /api/machines/:id/repositories` uses the existing client JWT, machine namespace and Runner RPC. An online Runner advertising `repositoryExport: 1` can export a fixed baseline; `repositoryImport: 1` adds independently verified target caches. `repositoryResults: 1` adds sealed result export. These operations do not start native sessions.

## Operations

- `export`: `{ action, operationId, source }`, where `source` is the fixed `WorkspaceSource` returned by the managed-workspace resolve operation. The source commit is required; export never resolves a moving branch again.
- `export-result`: `{ action, operationId, environmentId, roundId }` selects a result sealed by this Runner. Callers cannot supply or replace the result facts. Success includes `sealed: { source, result, verifiedAt }` and a complete independently verified snapshot.
- `import`: `{ action, operationId, snapshot, files: [{ name, path }] }`. Files must exactly match the snapshot and be present at allowed absolute paths, normally returned by artifact materialization. Success returns `imported.source` and the owned root/submodule cache mapping.
- `inspect`: `{ action, operationId }` returns the original operation, immutable snapshot and any error.
- `release`: `{ action, operationId, names? }` removes stopped export candidates or releases an import's cache holding. Names select exported files; import release requires omission. The receipt and snapshot remain queryable.

Export, result export and import return persisted `accepted` receipts and run in the background. Inspect reports `accepted`, `running`, `succeeded`, `failed` or `unknown`. Repeating the same ID and arguments returns the original receipt; different arguments conflict. A restarted Runner reconciles the saved Git process. Incomplete, stopped operations become explicit failures and are not automatically rerun. Use a new operation with the original snapshot after repairing the error. Inspecting a successful import also checks its source ownership and retained refs.

## Content and ownership

Files live under `HAPI_HOME/workspaces/exports/<operationId>/data/files`; the returned `directory` can be passed to the existing artifact capture API. Capture/deliver owns network transfer and center publication. Release candidates after publication is confirmed; releasing them is not an artifact deletion.

A snapshot identifies the source machine/repository and commit, each root/submodule bundle, and the baseline tree's required LFS entities. Every file has a stable name, length and SHA-256. Bundle references are generated by HAPI. No source URL, authentication material, ignored files, dirty worktree contents or project dependencies are copied.

Export uses scratch bare repositories with read-only source object alternates. Refs and LFS enumeration are confined to scratch data; source refs, index, configuration and working files are not modified. Source identity is rechecked at the fixed commit without refreshing dirty state. Git transport is disabled during object preparation, including partial-clone lazy fetch.

Full Git history reachable from the selected commit is exported. Shallow repositories, missing submodule commits and missing/corrupt LFS entities fail explicitly. Submodule objects must already exist in the source. LFS enumeration uses git-lfs when required, including custom source storage; repositories without LFS can export without that executable. Historical commits' LFS entities are not included unless required by the selected baseline tree.

A successful export means candidates are fixed. Import independently verifies bundle format, references and complete object closure before a workspace can be prepared.

## Sealed result export

Result export holds the managed repository lock used by prepare/remove/launch until all immutable candidates are captured and checked. It requires a retained owned checkout, a sealed round matching its preparation, matching immutable ref, a clean checkout at the latest sealed HEAD, reconciled workspace operations and verified native stop evidence. A new unsealed round or unknown execution blocks capture. The operation does not create a checkpoint, rewrite history or change the native runtime.

Capture reads the selected sealed commit from the checkout root, so deletion of the original task subdirectory does not lose the result. It reuses full root/recursive module/LFS export, then the same independent empty-store verifier as import. The verified Git history must contain base → start → result ancestry. Only then are `snapshot` and `sealed` persisted together. Scratch alternates and verification repositories are removed; candidate files remain for artifact delivery. No-change and partial results preserve their original facts. Changed or dirty submodules retain the existing workspace-finalize rejection policy.

Once successful, repeating the original operation or inspecting after Runner restart returns the same snapshot without reading the checkout again. Later rounds cannot change its files. An interrupted capture with no complete receipt fails after Git stop is proven; explicit new attempts still select the original sealed round. Release uses the existing partial/whole export cleanup, leaving workspace refs, commits, checkout and receipt untouched. Independent verification establishes machine candidates, not center delivery or business acceptance. Consumers must retain the initial baseline's LFS entities separately when those differ from the result tree.

## Target import and managed workspaces

Import first fixes and hashes the downloaded files under `workspaces/imports/<operationId>/data`, then imports each bundle into an empty bare verification repository without alternates or promisor configuration. Git must accept exactly the declared ref and commit, verify the bundle and pass object checking; a warm cache cannot supply missing prerequisite objects. The fixed tree must match the recursive gitlink and LFS manifest.

Verified objects enter `workspaces/repositories/<origin-key>/`. The key includes the Hub/authentication scope and source machine/repository identity. Multiple snapshots share caches; each has its own immutable ref. Import writes and managed-workspace operations use the same root repository lock. Bare HEAD stays on the initial `refs/heads/cache-base` and each environment has its own task branch/worktree. Import scratch data is removed on success; the caller can immediately release materialized downloads. Receipts remain under `workspaces/imports/<operationId>/operation.json`.

`imported.source` describes the target bare root, with the target machine/repository identity and `snapshot: { importOperationId, manifestId }`. It initially has `relativePath: ''`; a consumer may use its original source-relative cwd. Managed preparation validates that directory in the fixed commit and checks the saved import receipt, mapping and refs. It rejects a cache source with a missing or mismatched snapshot marker.

Pass this source to the existing workspace `prepare` operation. Submodules are initialized one level at a time from owned local caches, with checkout-scoped URL/active configuration; recursive names and relative upstream URLs cannot redirect downloads to the original source. LFS filters/storage are configured only in owned repositories, without requiring global filter configuration or installing hooks. Local entity copies and `lfs checkout` hydrate the files; cache workspaces never call `lfs pull`. Preparation hashes the resulting LFS bytes. Launch rechecks Git state, inputs, snapshot refs/gitlinks, and LFS checkout/downloaded flags without another full large-file hash scan.

Subsequent rounds use the existing finalize/prepare lifecycle and the last sealed result, including new local LFS objects. Original local workspace sources retain their existing behavior. Remote task orchestration and code-result delivery are separate consumer responsibilities.

## Cache release

Import release uses the same repository lock as import and managed workspaces. Environments using that import must already be removed, with no pending operations or result commits beyond their original baseline; otherwise release rejects and retains the holding. Other retained imports keep the shared cache. The response's `cache` reports the directory, retention and any reason.

Final cache removal also checks all owned environment records, Git worktree registrations and refs. Only refs matching saved snapshots, the original cache base and unchanged results of removed environments are disposable. Unknown refs, external worktrees or unrecognized entries preserve the cache and return a reason. Repair the reported condition and repeat the same release; this does not start a model or discard new code.

A checked cache is atomically moved to that import's owned `data/released-cache` before recursive deletion. Interrupted deletion resumes there; it cannot delete a later import which recreated the shared location. Import receipts remain queryable with `retention=released`; released sources cannot prepare or launch new workspaces. Center recovery pins are managed by the consuming coordinator, not by this machine API.
